# Measurement Observation Service

**Status:** Implemented and merged in PR #22; locally verified with 171 passing tests  
**Scope:** Observation data model, append-only repository, Unit-of-Work wiring, and the first manual-entry service

## 1. Purpose

The `measurement_observations` table and its migration are already part of the main branch. This implementation adds the application layer used to create and retrieve observations. It does not run a migration or change the existing daily-record workflow.

The observation layer records one metric value per row and keeps the reporting date, optional measurement time, platform recording time, canonical unit, source type and quality status explicit.

## 2. Supported first-release writes

`MeasurementObservationService.create_observation()` accepts only these six metrics:

| Metric | Canonical unit | Validation |
|---|---|---|
| `mortality` | `birds` | Non-negative whole-number count |
| `feed_kg` | `kg` | Non-negative finite number |
| `water_litres` | `litres` | Non-negative finite number |
| `average_weight_kg` | `kg_per_bird` | Positive finite number |
| `temperature_c` | `degrees_celsius` | Finite number; no new biological range limit |
| `humidity_percent` | `percent_relative_humidity` | Finite number from 0 to 100 |

The unit is derived from the metric name; callers cannot supply an arbitrary unit. Boolean values are rejected. Mortality must be a Python integer and must fit SQLite's signed integer range.

The first service release creates only:

- `source_type = 'manual_entry'`
- `quality_status = 'observed'`
- a generated UUID observation identifier
- a service-generated UTC `recorded_at` timestamp

Callers cannot choose other source or quality statuses through this service. A numeric zero is stored as an observed zero; it is never converted to NULL or interpreted as missing.

## 3. Dates, times and source linkage

- `record_date` must be an ISO calendar date in `YYYY-MM-DD` form. A Python `date` is also accepted.
- `observed_at` is optional. If supplied, it must be a timezone-aware Python datetime or ISO 8601 timestamp. The service normalises it to UTC. It does not infer measurement time from the reporting date.
- `recorded_at` is generated by the service in UTC when the observation is prepared for insertion.
- `daily_record_id` is optional. When supplied, the service verifies that the source daily record exists, belongs to the same flock, and has the same reporting date.
- The flock must exist before an observation is inserted.

No user identity is invented: `entered_by_user_id` remains NULL until authenticated identity is integrated. Device, import and calculation metadata also remain unset for manual entry.

## 4. Transaction and repository behaviour

The service uses the existing Unit of Work. The flock check, optional daily-record checks and observation insert share one `BEGIN IMMEDIATE` transaction and connection. A validation or insert error rolls the transaction back.

`MeasurementObservationRepository` exposes insert and read methods only:

- `create`
- `get_by_id`
- `get_by_flock`
- `get_by_daily_record`
- `get_by_flock_metric_date_range`

There are deliberately no repository update or delete methods. The database append-only triggers remain the final protection against direct row mutation.

Example:

```python
from datetime import date

from app.services.measurement_observation_service import (
    MeasurementObservationService,
)

service = MeasurementObservationService()
observation_id = service.create_observation(
    flock_id=1,
    record_date=date(2026, 11, 19),
    metric_name="feed_kg",
    value_numeric=12.5,
)
```

The example assumes that the database has already had the explicit schema migration applied by an approved operator. The service does not migrate or initialise databases automatically.

## 5. Explicit exclusions

This feature does not:

- dual-write observations when a daily record is created;
- change existing analytics or dashboards away from `daily_records`;
- backfill any historical daily records;
- change mortality's existing daily-record default or decide whether a default zero is confirmed evidence;
- create pending/rejected correction requests or quality-review events;
- implement accepted correction workflows;
- add Streamlit forms, sensor ingestion, file imports or system-generated observations;
- perform any operation against the developer's local production database.

These remain separately reviewable stages. In particular, the mortality-zero semantics, correction/review model and parent archive/deletion policy must be resolved before dual-write or backfill is enabled.

## 6. Test boundary

Service tests create a temporary SQLite database, initialise its baseline schema, and apply the migration to that test database. They cover the six metric/unit pairs, zero preservation, value validation, timezone handling, flock/daily-record references, date-range queries and the absence of update/delete repository methods.

The tests must never locate or open `data/poultryguard.db`.
